        60   def how_to_think_about_evaluation():
        61       You might think evaluation is a mechanical process (take existing model, throw prompts at it, average some
                 numbers)...
        62       Actually, evaluation is a profound and rich topic...
        63       ...and it determines the future of language models.
        64
        65       What's the point of evaluation?
        66       There is no one true evaluation; it depends on what question you're trying to answer.
        67      1. User or company wants to make a purchase decision (model A or model B) for their use case (e.g., customer
                   service chatbots).
        68      2. Researchers want to measure the raw capabilities of a model (e.g., intelligence).
        69      3. We want to understand the benefits + harms of a model (for business and policy reasons).
        70      4. Model developers want to get feedback to improve the model.
        71       In each case, there is an abstract goal that needs to be translated into a concrete evaluation.
        72
        73       Framework
        74      1. What are the inputs?
        75      2. How do call the language model?
        76      3. How do you evaluate the outputs?
        77      4. How to interpret the results?
        78
        79       What are the inputs?
        80      1. What use cases are covered?
        81      2. Do we have representation of difficult inputs in the tail?
        82      3. Are the inputs adapted to the model (e.g., multi-turn)?
        83
        84       How do you call the language model?
        85      1. How do you prompt the language model?
        86      2. Does the language model use chain-of-thought, tools, RAG, etc.?
        87      3. Are we evaluating the language model or an agentic system (model developer wants former, user wants
                     latter)?
        88
        89       How do you evaluate the outputs?

        90      1. Are the reference outputs used for evaluation error-free?
        91      2. What metrics do you use (e.g., pass@k)?
        92      3. How do you factor in cost (e.g., inference + training)?
        93      4. How do you factor in asymmetric errors (e.g., hallucinations in a medical setting)?
        94      5. How do you handle open-ended generation (no ground truth)?
        95
        96       How do you inteprret the metrics?
        97      1. How do you interpret a number (e.g., 91%) - is it ready for deployment?
        98      2. How do we assess generalization in the face of train-test overlap?
        99      3. Are we evaluating the final model or the method?
       100
       101       Summary: lots of questions to think through when doing evaluation

       103 def perplexity():
       104       Recall: that a language model is a probability distribution p(x) over sequences of tokens.
       105       Perplexity (1/p(D))^(1/|D|) measures whether p assigns high probability to some dataset D.
       106
       107       In pre-training, you minimize perplexity on the training set.
       108       The obvious thing is to measure perplexity on the test set.
       109
       110       Standard datasets: Penn Treebank (WSJ), WikiText-103 (Wikipedia), One Billion Word Benchmark (from
                 machine translation WMT11 - EuroParl, UN, news)
       111       Papers trained on a dataset (training split) and evaluated on the same dataset (test split)
       112       Pure CNNs+LSTMs on the One Billion Word Benchmark (perplexity 51.3 -> 30.0) [Jozefowicz+ 2016]
       113
       114       GPT-2 trained on WebText (40GB text, websites linked from Reddit), zero-shot on standard datasets
       115       This is out-of-distribution evaluation (but idea is that training covers a lot)
       116




       117       Works better on small datasets (transfer is helpful), but not larger datasets (1BW)
       118
       119       Since GPT-2 and GPT-3, language modeling papers have shifted more towards downstream task accuracy.
       120       But reasons why perplexity is still useful:
       121         Smoother than downstream task accuracy (for fitting scaling laws)
       122         Is universal (why we use it for training) whereas task accuracy might miss some nuances
       123           Note: can measure conditional perplexity on downstream task too (used for scaling laws) [Bhagia+ 2024]
       124
       125       Warning (if you're running a leaderboard): evaluator needs to trust the language model
       126       For task accuracy, can just take output generated from a blackbox model and compute the desired metrics
       127       For perplexity, need LM to generate probabilities and trust that they sum to 1 (even worse with UNKs back in
                 the day)
       128
       129       The perplexity maximalist view:
       130         Your true distribution is t, model is p
       131         Best possible perplexity is H(t) obtained iff p = t
       132           If have t, then solve all the tasks
       133           So by pushing down on perplexity, will eventually reach AGI
       134           Caveat: this might not be the most efficient way to get there (pushing down on parts of the distribution that
                 don't matter)
       135
       136       Things that are spiritually perplexity:
       137       Similar idea: cloze tasks like LAMBADA [Paperno+ 2016]
